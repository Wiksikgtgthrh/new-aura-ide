# Debugging

Цель — найти **причину**, а не заглушить симптом. Правка без понимания причины —
это не фикс, а гипотеза; так её и называй.

## 1. Зафиксируй факт

- Точный текст ошибки, stack trace, команда/шаги, ожидаемое и фактическое поведение.
- Окружение: версия рантайма, ОС, ветка, последние коммиты (`git log --oneline -10`).
- Не пересказывай ошибку своими словами — цитируй.

## 2. Воспроизведи

- Добейся стабильного воспроизведения одной командой. Это первая и главная задача.
- Сократи до минимального случая: убирай всё, что не влияет на баг.
- Не воспроизводится — скажи об этом прямо. Дальше только гипотезы с пометкой.
- Флаки: прогони N раз (`for i in $(seq 20); do <cmd> || break; done`), ищи порядок,
  время, общее состояние, сеть, параллельность.

## 3. Сузь

Выбирай самый дешёвый способ, который может опровергнуть гипотезу:
- Читай код по stack trace снизу вверх до первого кадра в коде проекта.
- Регрессия и есть рабочая версия — `git bisect` (`git bisect run <cmd>`), а не гадание.
- Логи в точке развилки: входные данные, ветка условия, результат. Префикс `[debug]`,
  удали после.
- Деление пополам: отключай половину пути данных, пока не найдёшь место.
- Проверяй допущения: версия пакета (`node_modules/<pkg>/package.json`), реальное
  значение env, реальный ответ API, реальный SQL.

Одна гипотеза за раз. Записывай: гипотеза → проверка → результат.
Две неудачные попытки одного подхода — смени подход, а не повторяй.

## 4. Найди первопричину

Спроси «почему» до уровня, где правка устраняет класс ошибок, а не один случай:
- неверные данные на входе? → валидация на границе;
- неверное допущение о типе/null? → тип и явная проверка;
- гонка/порядок? → синхронизация, идемпотентность, а не `setTimeout`;
- рассинхрон версий/кэша? → фиксация версии, инвалидация.

## 5. Исправь минимально

- Самая маленькая правка, устраняющая причину. Без попутного рефакторинга.
- **Сначала тест, который падает на баге** (скилл `testing`), потом фикс, потом тест зелёный.
- Проверь соседние места с тем же паттерном (`rg`), но правь их только по согласованию,
  если они вне задачи.

## Запрещено

- Глушить ошибку: пустой `catch`, `?.` везде, `// @ts-ignore`, `any`, `--force`,
  `eslint-disable`, отключение теста, повышение таймаута «на всякий».
- Объявлять «исправлено» без прогона воспроизведения после фикса.
- Удалять/переписывать тест, чтобы он прошёл.
- `git reset --hard`, `git clean`, удаление lock-файла/`node_modules` без понимания причины.

## Ответ

1. Причина — одним-двумя предложениями, с файлом и строкой.
2. Что изменено и почему это устраняет причину.
3. Доказательство: команда воспроизведения до (падает) и после (проходит), новый тест.
4. Что не проверено и какие риски остались.
