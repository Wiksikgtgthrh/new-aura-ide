# Backend & API

Опора — существующие паттерны проекта. Сначала найди, как в нём уже сделаны
роуты, доступ к БД, валидация и ошибки, и повторяй это. Не вводи второй ORM,
второй валидатор или второй формат ошибок.

## Граница (каждый вход извне)

- **Валидация схемой** на входе (zod/valibot/pydantic) — тело, query, params, заголовки
  вебхука. Дальше по коду идут уже проверенные типы.
- **Аутентификация и авторизация** в каждом эндпоинте, а не только в UI. Проверяй
  владельца ресурса: `WHERE id = $1 AND user_id = $session` — иначе IDOR.
- Никогда не доверяй клиенту: цена, роль, `userId`, количество — берутся/пересчитываются
  на сервере.
- Вебхуки — проверка подписи до любой обработки; ответ быстро, тяжёлое — в фон.
- Лимиты: размер тела, rate limit на логин/формы/дорогие операции.

## Данные

- Только параметризованные запросы. Конкатенация SQL — блокер.
- **Миграции** — отдельным файлом, вперёд и с планом отката. Разрушающие изменения
  (drop, rename, NOT NULL на заполненной таблице) — по шагам: добавить → заполнить →
  переключить → удалить. Запуск на проде — только с подтверждением (`data-safety`).
- Индексы под реальные `WHERE`/`JOIN`/`ORDER BY`. Внешние ключи и уникальность — в БД,
  а не только в коде.
- Несколько связанных записей — одна транзакция.
- Деньги — целые минимальные единицы или decimal, не float. Время — UTC в БД.

## Производительность

- **N+1**: запрос в цикле — заменить на `IN (...)`/join/батч. Проверь по логу запросов.
- Пагинация обязательна для списков; на больших таблицах — курсорная, а не `OFFSET`.
- Выбирай только нужные колонки. Тяжёлое — в фон/очередь с ретраями.
- Кэш — только с понятной инвалидацией и ключом, включающим пользователя, если данные личные.

## Надёжность

- **Идемпотентность** для операций с внешним эффектом (оплата, письмо, создание заказа):
  ключ идемпотентности или уникальное ограничение.
- Внешние вызовы: таймаут, ограниченные ретраи с backoff только для transient-ошибок.
- Ошибки: единый формат ответа, корректные коды (400 валидация, 401/403 доступ, 404, 409
  конфликт, 422, 429, 5xx). Клиенту — без stack trace и SQL; в лог — с контекстом и id запроса.
- Секреты — только из env, никогда в коде, логах и ответах.

## Проверка

- Тесты интеграционного уровня на эндпоинт: успех, невалидный ввод, чужой ресурс (403/404),
  без авторизации (401), конфликт/дубль (скилл `testing`).
- Ручная проверка реальным запросом (`curl -i`), с кодом ответа и телом в отчёте.
- Для изменений схемы — прогон миграции на чистой и на заполненной тестовой БД.

## Ответ

Что изменено (роуты, схема, миграции), как защищена граница (валидация, доступ),
команды проверки и результат, риски миграции и план отката.
