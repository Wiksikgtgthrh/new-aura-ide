## Блокер

### ZAN-8 «закрыт» фиксом, который убил разрезку кадров — BLOCKER, видео мертво целиком

`src/deviceScreen.ts:210-212` (isFirstSlice), вызов `:227`; в билде `out/deviceScreen.js:277,293`.

```ts
private static isFirstSlice(buf: Buffer, headerEnd: number): boolean {
    return headerEnd < buf.length && (buf[headerEnd] & 0x80) !== 0;
}
```

`nextNal` возвращает `headerEnd` = **индекс байта заголовка NAL** (это видно из самого же кода: `type = buf[headerEnd] & 0x1f` читает тип именно из него, а `codecFromSps` комментирует «sps[0] — заголовок NAL»). `first_mb_in_slice` живёт в **slice header**, который начинается на байт позже: `buf[headerEnd + 1]`. Проверка `buf[headerEnd] & 0x80` читает **forbidden_zero_bit** — в валидном H.264 он всегда 0 (RFC 6184 §1.3, §5.3: NAL-заголовок = один байт `F|NRI|Type`, F обязан быть 0).

**Следствие:** `isFirstSlice` возвращает false для КАЖДОГО слайса → `cut` не находится никогда → `onVideoData` не эмитит ни одного `video-chunk`, ни одного `video-config` → webview остаётся на пустой img-поверхности, без кадров, без offline-индикатора, без ухода в фолбэк (нет ошибки — нет `video-error`). pending копится до 16 МБ и сбрасывается, по кругу. screenrecord продолжается и перезапускается каждые 180 с — впустую.

**Живое доказательство** (собранный артефакт `out/deviceScreen.js`, синтетический Annex-B поток: SPS+PPS+IDR, кадр 2, многослайсный кадр 3, хвост кадра 4):

- `isFirstSlice(first_mb_in_slice=0)` → **false** (должно true)
- конвейер `onVideoData` → **0 кадров, 0 video-config** (ожидалось 3)
- то же с единственной правкой `buf[headerEnd + 1] & 0x80` → **ровно 3 кадра**, многослайсный кадр собран одним AU, key/delta размечены верно

В b1 парсер работал на монослайсных кадрах (мое «Подтверждено» в ZAN-b1: «разрез AU по следующему слайсу»). Регрессия подтверждённой ACCEPT-зоны.

**Фикс:** `return headerEnd + 1 < buf.length && (buf[headerEnd + 1] & 0x80) !== 0;` — и зелёный S1/S2 смоука.

### ZAN-6 (дроп чанков ломает референс-цепь) — НЕ ЗАКРЫТ, «фикс» сделан хуже проблемы
webview `feedChunk` (`html` ~`:459-468`):

```js
if (decoder.decodeQueueSize > 60) {
    if (msg.key) { try { decoder.reset(); } catch(e) {} }
    else { return; }
}
try { decoder.decode(new EncodedVideoChunk({...})) } catch (err) { decoder = null; video-error }
```

Две независимые ошибки:

1. **`reset()` по спеке переводит декодер в unconfigured, а следующий `decode()` бросает InvalidStateError.** W3C WebCodecs (WD от 07.10.2026, §VideoDecoder): «reset(): Immediately resets all state **including configuration**…» — алгоритм Reset VideoDecoder, шаг 2: «Set state to "unconfigured"»; decode(): «If state is not "configured", throw an InvalidStateError». То есть путь «перегрузка → пришёл key → reset → decode» **гарантированно** кидает InvalidStateError → catch → `decoder = null` + `video-error` → `fallbackToImages()` навсегда. В b1 перегрузка убивала видео при лаге с некоторой вероятностью; в b1fix она убивает его с вероятностью 1 при первом же срабатывании. Комментарий «reset бросает если уже closed — ок» показывает, что семантику reset() не проверяли.
2. Коммент «не-ключевой при перегрузке: пропускаем до следующего IDR» неверен: скип длится только пока `decodeQueueSize > 60`. Если бэклог стечёт раньше следующего IDR (60 кадров ~2 с, IDR у screenrecord редкий), следующие дельты уйдут в `decode()` с разорванной референс-цепью — исходная проблема ZAN-6 осталась.

**Фикс:** флаг `skipUntilKey = true` при первом превышении порога; в этом состоянии — `reset()` **и повторный `configure(codec)`** (или пересоздание декодера через существующий `resetDecoder`), дроп ВСЕХ чанков до первого `key`, затем decode ключа и сброс флага.

## Источники

- W3C WebCodecs, Working Draft 07.10.2026: `reset()` — «Immediately resets all state **including configuration**»; Reset VideoDecoder шаг 2 — state → "unconfigured"; `decode()` — InvalidStateError, если state ≠ "configured" (w3c.github.io/webcodecs/#dom-videodecoder-reset)
- RFC 6184 (RTP Payload for H.264): §1.3/§5.3 — NAL-заголовок = один байт `F|NRI|Type`, forbidden_zero_bit = 0 обязателен; §1.1 — slice header содержит адрес первого макроблока (first_mb_in_slice), идёт ПОСЛЕ заголовка NAL
- Внутренняя согласованность кода: `codecFromSps` (`:264`) сам комментирует «sps[0] — заголовок NAL, sps[1] — profile_idc» — то же смещение, что isFirstSlice обязан использовать, но не использует
- AOSP-цитаты ZAN-b1 (wm size / DisplayContent / screenrecord 180 с) — не оспорены билдером, остались в силе
